# 水道メーター読み取り PoC（方式A: 学習済み検出器 + 合成データCNN）

## 手順
```
pip install -r requirements.txt
python synth_digits.py        # 合成データ生成 (data/synth/)
python train_digit_cnn.py     # 学習 → digit_cnn.onnx (約 580KB)
python synth_red_digits.py    # 赤い小数桁用の合成データ生成 (data/synth_red/)
DATA=data/synth_red OUT=digit_cnn_red.onnx FLIP=0 python train_digit_cnn.py   # 赤桁用 → digit_cnn_red.onnx (約 580KB)
python read_meter.py photo.jpg --digits 8 --red 3 --debug
```
`--digits` は数字窓の桁数、`--red` は右端の小数桁（赤字）の数。
`--debug` で検出枠 (debug_box.jpg)、正面化した窓 (debug_window.png)、分割した各桁 (debug_cells.png) を出力。

## 構成
- 検出: PP-OCR DB (MobileNet) 学習済み ONNX（rapidocr-onnxruntime 同梱） → `pick_counter_window` でアスペクト比・暗さ・サイズでスコアリング
- 認識: ドラム帯をシミュレートした合成データ (0-9 静止 / 10+d 回転中) で学習した3層CNN、ONNX Runtime で実行
- 赤い小数桁だけは専用モデル `digit_cnn_red.onnx`（同じ構造・同じ 20 クラス）で読む。入力は赤みチャネル（下の「赤い小数桁の専用モデル」）。
  モデルが無ければ警告を 1 回出して従来どおり黒桁のモデルで読む
- 回転中は小さい方の値 d を採用し、その右側の桁は 9 に揃える（切り捨て読み）
- 桁分割は列投影のピークに各セル中心を合わせる（検出枠の余白によるズレ対策）

## 端末移植
- 検出器: rapidocr 同梱の det ONNX モデル (約4.7MB) をそのまま ONNX Runtime Mobile へ
- 認識器: digit_cnn.onnx（約 580KB。以前の「約 20KB」は誤記）と digit_cnn_red.onnx（約 580KB）をそのまま。赤桁の前処理 `red_input.py` は numpy の数行なので書き直しやすい。iOS は Core ML 変換 (coremltools) でも可

## 合成データで効いた調整（実写を見て直した点）
- ドラム帯から窓を切り出す生成方式（上下に隣の数字がのぞく状態を「静止」として学習）
- 数字の高さをピッチの 62〜95% に（実機は密）
- 太字: stroke_width で肉付け
- 上が平らな「3」を描画で追加（フォントの丸い3だけだと 5 と誤認）
- 小数点・隣セルのドットが角に入る augmentation
- 「左の縦線＋上のフック」型の 6（と上下反転の 9）を描画で追加（丸い 6 だけだと 5 と誤認）

## 検出・分割で効いた調整（2枚目で直した点）
- 文字検出器は「白地に赤」の小数桁を取りこぼす → カラーの赤マスクで窓の右隣の赤を探し、枠をそこまで伸ばす
- 数字窓の選択は「暗さ」を最重視（桁数ぴったりの縦横比を求めると型番ラベルに負ける）
- 黒い桁と赤い桁を別々に分割。黒は列投影のピーク→白が連続する区間の中点（0 や 8 の中空対策）、赤は赤マスクの中心→白い箱の中点
- セルの白黒反転は画像から推定せず、構造で決め打ち（黒い桁＝反転なし、赤い桁＝反転）。
  明るさ統計で判定すると反射やドラムの隙間の影で誤判定する。白地の機種は `--invert`
- 推論時は位置ずらし 5 パターン × 白黒 2 通り = 10 パターンの平均（TTA）。数 ms で済む

## 3枚目で直した点
- 「上が開いた4」を描画で追加、セルを囲む枠線の augmentation を追加（赤い桁は箱の中にある）
- 試して戻したもの: コントラスト正規化（枠線を強調して悪化）、低解像度化 augmentation（全体が悪化）

## 4枚目と堅牢化で直した点
- 赤い桁の探索を窓の右側（黒い桁の領域より右）に限定: 天地逆や窓の左に赤い物があると、左の赤を桁と誤認して空セルができ cv2.resize で落ちていた
  - 赤探索の下限は黒桁領域の境界から h*0.8 手前（斜めの写真で赤い桁が左に寄っても拾えるように）
- セル幅（2px 以上）と黒い桁の領域（等分割の半分以上）に下限を付け、空セルを防止（`_cut_cell` も幅 0 にならないように）
- 画像を読み込めないときは「画像を読み込めません: パス」を出して終了コード 1。`cv2.imdecode` + `np.fromfile` で Windows の非 ASCII パスにも対応
- `digit_cnn.onnx` をスクリプトの場所基準で読むようにし、別ディレクトリからでも実行可能に
- `--digits` は 1 以上、`--red` は 0 以上 `--digits` 未満であることを検証（満たさなければ引数エラー）

## 検出後処理の改善（合成ベンチマーク）
`in/meter4.jpg` から合成した 228 ケース（回転・露出・ガンマ・コントラスト・ぼかし・縮小・遠近・クロップ・組み合わせ）を、検出から通して採点した。
黒桁正解率は 0.417 → 0.860、strict（0041.2 完全一致）は 0.206 → 0.224。正解枠を渡したときの値（黒桁 0.89 / strict 0.35）は変わらない。
後段の処理時間は meter4 で 19 → 21 ms（検出は約 250 ms）。実写は meter4 の 1 枚だけで、**合成ベンチマークはすべてこの 1 枚由来**なので、他機種・他の撮影条件での効果は未確認（meter1〜3 の再確認もできていない）。

- 検出枠の上下の辺を、黒桁の列の「白インクの行」の帯の上下縁に合わせ直す（`refine_vertical`）。枠が数 px ずれると上の桁の下端がセルに入って 4→1 などに化けていた。失敗したら元の枠を使う
  - 赤い桁のセルは精緻化前の枠から切る（`split_digits` の `win_red`）。回転中の赤桁は切り出しの違いで 12 と 6 の間を揺れ、精緻化後の窓から切ると strict が 0.10 まで落ちた
- 赤マスクを、HSV の絶対しきい値から「R−max(G,B) の上位 0.5% と雑音（90%）の内分」に変更。赤拡張を窓座標系で探すようにして、傾き・天地に依存せず、画像全体の HSV 変換をやめて速くなった。赤が見つからないときは右端ではなく黒桁のピッチから外挿
- 縦長の検出枠は点を 1 つ回して横長の窓として評価（90° 回転の写真）。0° と 180° の両方を読み、「白い箱の中の赤」が右端にある方を採る。赤で決まらなければ黒桁の信頼度が 0.2 以上高いときだけ 180°
- レビュー指摘の修正（黒桁 0.860 → 0.864、strict 0.224 のまま）
  - 赤なし判定を `peak < 3*noise+4` から `peak - noise < 15` に変更（`red_mask`）。探索範囲に文字盤が入ると noise が高く（素の meter4 で 17）、暖色かぶり +10 で赤なしと誤判定していた。窓だけを見る `split_digits` は差 10 に下げる（低コントラストの赤桁は peak が 12 程度）
  - 差で判定すると窓の右の文字盤の微小な赤み（面積 15〜17）を拾い拡張が 2 倍近く伸びたので、探索範囲で最大の塊の 1/10 未満の塊は捨てる。帯を縦に横切る赤い針（探索範囲の上下端に届く塊・高さ 1.2 unit 超）も捨てる（`extend_to_red_digits`）
  - 赤が見つからず外挿するとき、白い箱の左端の手前で黒桁の探索を打ち切る（`_white_box_left`）。箱の左半分を黒桁のピークに拾って 1 桁ずれていた（赤桁を白で塗ると 0411.5 → 0041.4）
  - `_cut_cell` はセルが窓の右に完全にはみ出しても端の 1 列を複製する。`locate_and_read` が捕まえる例外を `cv2.error, ValueError, IndexError, ZeroDivisionError` に絞り、失敗した向きは `cand` の `err` として `window:` 行の下に表示する
  - 上下に広げるときは左右の辺それぞれのベクトルを使う（台形の枠で辺がずれない）
  - 試して戻した: 赤なし判定を差 15 一律にすると低コントラストの赤桁（combo_035）が外挿に落ち、微小な赤みを拾う（combo_066, 111）ことで黒桁が 0.851 に下がったため、上記の分離にした
- 既知の限界: 赤桁の無い機種（`--red 0`）の 180° 写真はほぼ直らない。白い文字盤の機種の精緻化は模擬画像 1 枚でしか確認していない

| 条件 | 黒桁 前 → 後 | strict 前 → 後 |
|---|---|---|
| 全体（228） | 0.417 → 0.860 | 0.206 → 0.224 |
| 回転（15） | 0.40 → 0.93 | 0.20 → 0.33 |
| 組み合わせ（160） | 0.34 → 0.82 | 0.16 → 0.18 |
| 遠近（20） | 0.70 → 1.00 | 0.45 → 0.45 |

試して戻したもの:
- 黒帯の暗さで縁を出す方式: 文字盤も黒く、窓の内外で暗さが区別できなかったので、インクの有無に変更
- 枠を上下にずらした複数仮説を黒桁の信頼度で選ぶ方式（vshift）: 黒桁は良くなるが赤桁が 6 に寄って strict がほぼ 0 になり、後段が 3〜10 倍かかる
- 左右半分で帯を求めて傾きを直線フィット: 黒桁 0.605 と悪化。検出枠の傾きのほうが正確
- Otsu による赤しきい値: 赤が数 % しかなくヒストグラムが片寄り、しきい値が雑音のすぐ上に張り付く
- 黒桁の信頼度だけで向きを決める: 逆さの 0 や 1 も高い信頼度で読むので、正しい向きなのに 27% で逆を選んだ

## 赤い小数桁の専用モデル
合成ベンチマークで strict（0041.2 完全一致）が 0.224 に留まった原因は赤桁で、黒桁が正しい 197 件のうち赤桁を 6 と読むのが 135 件、12 は 51 件だった（誤りの 7 割が「12 → 6」）。
赤桁は黒桁と**別の書体**（細い・直線的な工業用の数字が、白い箱の中に赤で書かれ、枠線・目盛り帯・▶ が付く）なので、同じ CNN で両方を読むのをやめ、赤桁だけ専用モデルにした。

- **前処理**: 赤セルは反転グレーではなく `R − max(G, B)`（赤みチャネル）を 5%/99% 点で 0〜255 に伸ばしたもの（`red_input.py`。学習と推論で同じ関数）。
  灰・黒・白（箱の枠、目盛り帯、▶、黒い文字盤）は 0 に消え、字だけが黒地に明るく残る（極性は黒桁モデルと同じ）。
  反転グレーでは箱の中の暗い灰・箱の外の明るい灰・目盛り帯が字と同程度に入り、字そのものは薄かった。
  赤みの幅（99% 点 − 5% 点）が 8 未満なら「赤が無い」として従来の黒モデル + 反転グレーに戻す（ベンチの赤セルは最小 13 なので、この分岐はベンチでは確かめていない）
  - 要検証: `RED_EMPTY=8` の判定は、暖色かぶりで赤の無いセルも赤みの幅が 8 を超えて赤モデルに回りうる（赤モデルは過信気味で、そうしたセルにも 12 を高信頼度で返す）
- **合成データ**（`synth_red_digits.py`）: 角型数字 75%・既存フォント字形 25%（角型への過学習の防止と、現物が角型でない場合の保険）。
  字幅/字高 0.50〜0.65、線幅/字高 0.09〜0.15、字高/ピッチ 0.72〜0.92（いずれも meter4 の実測 0.62 / 0.12 / 0.82 を中心に）。
  白い箱に赤字、箱の枠線、右端の目盛り帯と▶、黒桁の切れ端、色かぶり・彩度低下・JPEG などカラーのまま汚してから、推論と同じ INTER_AREA で 28×40 に縮小して前処理をかける。
  20 クラス × 2500 枚。学習は `FLIP=0`（赤みチャネルは常に黒地に明るい字なので、明暗反転の augmentation を切る）
- **注意: 字形は「一般的な角型数字」を手で設計したもので、現物の書体は未確認**。実写は meter4 の 2→3 の 1 枚だけで、その字は角が大きく丸い。
  角の様式の比率（sharp 20% / chamfer 25% / round 55%）も推測。写真が手に入ったら `glyph_paths` の座標と比率を直す
- 推論: 赤セルはカラーのまま切り出し（`split_digits` の `info["red_color_cells"]`）、`classify_cells` で赤モデルに通す。位置ずらし 5 パターンは残し、両極性は使わない。黒桁の経路は変えていない
- **合成テスト**（seed 12345、200 枚/クラス、学習と別の乱数）: 正解率 0.989（角型 0.991、フォント 0.984）。学習の val_acc は 12 エポックで 0.992、学習 95 秒。
  12↔6、13↔8、12↔2、13↔3、5↔6、0↔8 の取り違えはほぼ 0（最大でも 6→5 の 1/200）。主な誤りは 19↔15 と 11→7 の各 2 件
- **meter4**: 赤桁 (12, 0.49) → (12, 1.00)。黒桁の per-digit は (0,1.0)(0,1.0)(4,0.8)(1,1.0) のまま。後段の処理時間は約 14 → 15 ms
